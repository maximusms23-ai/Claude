### 1.2 claude-memory-compiler als Infrastruktur-Baustein

**Was es ist:** Ein Open-Source-Tool von Cole Medin (https://github.com/coleam00/claude-memory-compiler), das Claude-Code-Konversationen automatisch in Karpathy-Style-Wissensartikel kompiliert.

**Wie es läuft:**

1. **SessionEnd-Hook** (bei jedem Ende einer Claude-Code-Session): liest Transcript → schreibt Rohlog nach `95_Gehirn/daily/YYYY-MM-DD.md`. Hook kehrt in <10 s zurück, der eigentliche Write läuft detached im Hintergrund via `subprocess.Popen`.
2. **`compile.py`** (manuell oder täglich via Cron): nimmt alle neuen daily-Entries seit letztem Lauf, destilliert sie via Claude Agent SDK in Konzept-Artikel (`knowledge/concepts/*.md`) und Verbindungen (`knowledge/connections/*.md`).
3. **`query.py`** (Teil des Tools, wird bei uns noch nicht aktiv genutzt): Index-first-Abfrage via Claude Agent SDK.
4. **`lint.py`**: Strukturcheck auf Broken Links, Orphans, Stale-Artikel, Sparse-Artikel, Contradictions. Wir rufen das bei uns via `tom-lint [--structural-only]` auf.

**Wo es bei uns lebt:** `/Users/maxim/Claude/claude-memory-compiler/` — als Git-tracked Verzeichnis im Main-Repo (kein nested `.git`, keine Submodule, einfache Files). Die Upstream-Änderungen sind via `TOM-PATCHES.md` dokumentiert mit Merge-Anleitung.

**Was wir gepatcht haben (6 Punkte, alle minimal):**

1. `scripts/config.py` — `TOM_VAULT` Env-Var + alle Content-Pfade zeigen auf `$TOM_VAULT/95_Gehirn/` statt ins Tool-Repo
2. `hooks/session-start.py` — Paths kommen via `sys.path.insert + from config import`, statt hardcoded `ROOT / "daily"`
3. `hooks/session-end.py` — dito
4. `scripts/flush.py` — dito (das ist der Writer, der gepatcht werden **musste**, sonst hätte er trotz config-Patch weiter ins Tool-Repo geschrieben)
5. `tom_tools/wiki_query.py` — **neues Modul**, das lokal via Ollama (`gemme`) statt Claude Agent SDK arbeitet (siehe 1.5)
6. `pyproject.toml` + `uv.lock` — `ollama>=0.6.1` als Dependency für Punkt 5

**Kosten-Frage:** Der Compiler nutzt für die Destillation die Claude Agent SDK. Laut Cole Medin (Upstream-README) und laut Maxims ursprünglicher Message ist **Personal-Use unter der Claude-Subscription gedeckt**. Das ist non-blocker für v1.2, sollte aber vom CEO verifiziert werden — siehe "Offene Klärungen" unten.

### 1.3 Die Claude-Code-Hook-Integration

**Das Problem, das wir vermeiden mussten:** Globale `~/.claude/settings.json` hat bereits zwei Hooks:
- `SessionStart → gsd-check-update.js` (GSD Workflow-Tooling)
- `PreToolUse → rtk-rewrite.sh` (RTK Token-Killer)

Wenn wir diese globale Config anfassen, riskieren wir, Maxims bestehende Infrastruktur zu brechen — GSD ist der Workflow, RTK spart laufend Tokens.

**Unsere Lösung:** Projekt-lokale Hooks in `/Users/maxim/Claude/.claude/settings.json`. Claude Code merged projekt-lokale und globale Hooks automatisch — **beide** laufen dann parallel.

Wir haben drei Hooks eingetragen, alle zeigen mit absoluten Pfaden in den Compiler:

```json
{
  "hooks": {
    "SessionStart": [{ "command": "uv run --directory /Users/maxim/Claude/claude-memory-compiler python hooks/session-start.py" }],
    "PreCompact":   [{ "command": "uv run --directory /Users/maxim/Claude/claude-memory-compiler python hooks/pre-compact.py" }],
    "SessionEnd":   [{ "command": "uv run --directory /Users/maxim/Claude/claude-memory-compiler python hooks/session-end.py" }]
  }
}
```

**Verifikation, dass das läuft:**
1. **Direct-Import-Smoke-Test** aller drei Hook-Files: OK, keine ImportErrors, Pfade zeigen korrekt ins Vault-Brain
2. **`session-start.py` manuell aufgerufen**: liefert tatsächlich den Brain-Index als `additionalContext` zurück
3. **`rtk --version`**: 0.35.0 funktioniert weiterhin → RTK nicht gebrochen
4. **Globale `~/.claude/settings.json` unverändert**: GSD-Hook noch aktiv
5. **Nebenbefund — der Beweis, dass HOOK-03 in Produktion funktioniert:** Beim Lint-Run in Phase 19 wurde ein daily-log gefunden: `$TOM_VAULT/95_Gehirn/daily/2026-04-10.md` mit dem Inhalt *"FLUSH_OK - Nothing worth saving from this session"*. Den hat **nicht** mein Code geschrieben — den hat der echte SessionEnd-Hook beim Python-Import-Test in Phase 16 geschrieben. Das heißt: der End-to-End-Flow (Claude Code → Hook → flush.py → daily-log-File in iCloud-Vault) ist bereits einmal erfolgreich durchgelaufen. Das hat Phase 16 retrospektiv von `human_needed` auf `passed` aufgewertet.

### 1.4 Der 90_Wiki-Index-Umbau (Karpathy-Methode)

**Vorher:** `90_Wiki/index.md` war ein Changelog — eine Tabelle mit "was wurde wann geändert". Nützlich zum Tracken, aber **nicht** als Retrieval-Instrument.

**Jetzt:** `90_Wiki/index.md` ist ein **Karpathy-Retrieval-Index** im Stil, den Andrej Karpathy in seinen Tweets/Videos propagiert:

1. Am Anfang steht eine Bedienungsanleitung für das LLM: *"Lies zuerst diesen Index, wähle 3–5 relevante Artikel per Wikilink, lies die Artikel direkt, synthesisiere die Antwort."*
2. Dann gruppiert nach Kategorie (Konzepte, Themen, Projekte, Quellen, Personen, Meta)
3. Jeder Artikel mit **einer 1–2-Zeilen-Beschreibung**, die gerade genug Kontext für Routing gibt, aber nicht so viel dass der Index selbst zu schwer wird
4. Der alte Changelog lebt weiter in `90_Wiki/history.md` (nicht verloren, nur aus der primären Navigation verbannt)

**Warum das bei unserer Größe besser ist als RAG:** Bei 14–500 Artikeln ist LLM-Reasoning über gezielte File-Reads **präziser** als Cosine-Similarity. Cosine findet "ähnlich klingende" Chunks; LLM-Index-Navigation findet "das ist wirklich die Antwort". Erst ab ~500 Artikeln wird der Index zu schwer für einen Prompt und RAG-Primary wird sinnvoll.

**Smoke-Test, der das belegt:** Frage *"Was ist TurboQuant?"* → Index verweist auf `konzepte/turboquant.md` → direkter `Read` des Artikels liefert den vollständigen Google-Research-KV-Cache-Quantisierungs-Kontext → Antwort synthesisierbar. **Ohne RAG, ohne ChromaDB, mit 2 File-Reads.**

### 1.5 Das tom-wiki Tool — lokal, kostenlos, Index-first

Cole Medins Original-`query.py` nutzt die **Claude Agent SDK** (= Claude-API). Das geht aufs Subscription-Kontingent, ist aber teurer als nötig für unsere Brain-Größe.

**Unser Ansatz:** Eigenes Modul `claude-memory-compiler/tom_tools/wiki_query.py`, das stattdessen **lokal via Ollama** arbeitet:

1. Liest den Index + **alle** Artikel eines Wiki-Roots (`90_Wiki/` oder `95_Gehirn/`) in einen einzigen Prompt
2. Schickt das an `gemme` (unser Custom-Model auf Basis von `gemma4:e4b`, 128k Kontext)
3. Gemme antwortet auf Deutsch, zitiert Quellen per Wikilink
4. Wenn das Wiki > 100k Chars wird, trimmt das Tool und empfiehlt `tom-ask` als Fallback

**Drei neue Bash-Wrapper, alle in `bin/` + Symlinks in `~/bin/`:**

| Tool | Zweck | Backend |
|---|---|---|
| `tom-wiki "Frage"` | Karpathy Index-first über `90_Wiki/` | Lokal via `gemme` |
| `tom-wiki --brain "Frage"` | Karpathy Index-first über `95_Gehirn/` | Lokal via `gemme` |
| `tom-compile` | daily-logs → knowledge-Artikel | Claude Agent SDK (Subscription) |
| `tom-lint [--structural-only]` | Brain-Health-Check | Lokal (keine LLM-Calls) |

Das ergibt die **Wissens-Kaskade**, die jetzt in `CLAUDE.md` und `AGENTS.md` dokumentiert ist:

1. **Direct-Read** für persönliche/aktuelle Daten (`40_Aufgaben/TODOS.md`, `10_Personen/*`) — schneller als jedes Tool
2. **`tom-wiki "Frage"`** für bekannte öffentliche Wiki-Themen — präzise via Index
3. **`tom-wiki --brain "Frage"`** für Konversations-Wissen aus früheren Sessions
4. **`tom-ask "Frage"`** als RAG-Fallback für fuzzy oder Vokabular-mismatchende Queries

### 1.7 Multi-Projekt-Konvention — `wiki_path`

Das Brain soll **nicht** auf `/Users/maxim/Claude/` beschränkt bleiben. Andere Projekte auf dem Mac sollen es als Wissensquelle nutzen können — sowohl lesend als auch schreibend.

**Die Konvention (in `claude-memory-compiler/docs/multi-project.md`):**

Ein fremdes Projekt fügt in seine `CLAUDE.md` eine "Wissensquelle: Tom-Vault"-Sektion ein, die auf `$TOM_VAULT` zeigt und die drei `tom-*`-Tools auflistet. Damit kann dieses Projekt Tom's Wissen lesen.

Wenn das Projekt zusätzlich **eigene daily-Logs** ins zentrale Brain beitragen soll (empfohlen für Projekte, in denen regelmäßig mit Claude Code gearbeitet wird), legt es eine eigene `.claude/settings.json` an, die **ebenfalls** auf den zentralen `claude-memory-compiler` zeigt. Alle teilnehmenden Projekte schreiben dann in **denselben** `95_Gehirn/daily/`. `compile.py` kompiliert projekt-übergreifend. **Wissen wird global, nicht projekt-lokal.**

**Erstes Demonstrations-Projekt:** `/Users/maxim/Claude/Gemma/CLAUDE.md` — das Gemma-Sub-Projekt hat jetzt seine eigene Instructions-Datei mit voller Wissens-Kaskade-Sektion. Smoke-Test `cd Gemma && tom-wiki "Frage"` funktioniert korrekt aus fremdem cwd heraus, weil die Wrapper ihren eigenen `TOM_VAULT` und `cd` setzen.

## Teil 3 — Ehrliche Trade-offs & Risiken

Ich bin hier bewusst selbstkritisch. Vier Punkte, die nicht verschweigt gehören:

### 3.1 `tom-wiki` Antwort-Qualität ist noch mittelmäßig

Der Smoke-Test mit *"Was ist TurboQuant?"* hat funktioniert — das Tool lief durch, es kam eine deutsche Antwort, die Quellen wurden gelistet. **Aber:** Die Antwort war teils generisch. `gemme` hat allgemeines Quantisierungs-Wissen gemischt mit dem spezifischen TurboQuant-Artikel. Bei der Query ist eine echte Karpathy-Synthese nicht perfekt gelungen.

**Woran das liegt:** `gemme` ist auf Gemma 4 (e4b) basierend trainiert, hat generelles Weltwissen. Wenn der Prompt zu lang ist und die Anweisung "nutze nur den Context" nicht stark genug greift, driftet das Modell.

**Mitigation für v1.3:**
- Stärkerer System-Prompt
- Kleinerer Context (nur wirklich relevante Artikel statt alle)
- Ggf. ein besseres Modell einsetzen, sobald verfügbar
- Eval-Framework aus v1.1 einsetzen, um tom-wiki vs. tom-ask quantitativ zu vergleichen

Das ist **nicht v1.2-blockierend** — das Tool läuft, die Infrastruktur ist richtig. Die Feinjustierung gehört in einen nächsten Milestone.

### 3.2 Memory-Compiler-Kosten unbestätigt

Die Claude Agent SDK, die `compile.py` nutzt, ist **laut Cole Medins README** und laut Maxims Original-Message von der Claude-Subscription gedeckt — keine extra API-Kosten. Ich habe das nicht unabhängig mit Anthropic verifiziert.

**Warum das relevant ist:** Wenn die Annahme falsch ist, generiert jeder Compile-Lauf laufende Kosten. Das wäre kein Desaster, aber es verändert die Ökonomie des Auto-Capture erheblich.

**Was der CEO tun sollte:** Kurze Verifikation bei Anthropic-Support oder in den Terms lesen. Konkrete Frage: *"Personal-Use der Claude Agent SDK in einem lokalen Tool, das aus Claude-Code-Sessions Konzept-Artikel destilliert — ist das von der Claude Max Subscription gedeckt, oder sind das separate API-Calls mit eigenem Billing?"*

`compile.py` hat eingebautes Cost-Tracking im `state.json` — wir können periodisch prüfen, wieviel bisher angefallen ist. Der aktuelle Wert ist `0.0`, weil wir noch keinen Compile-Lauf gemacht haben.

### 3.3 iCloud-Latenz als stiller Killer

Die daily-Logs werden nach `$TOM_VAULT/95_Gehirn/daily/` geschrieben — also **in den iCloud-Sync-Ordner**. Wenn Maxim offline ist, oder wenn iCloud einen Sync-Backlog hat, können Writes sich stauen.

**Aktuelle Beobachtung:** Bisher kein Problem. Der Test-Write in Phase 16 ging sofort durch. Aber es ist ein latentes Risiko.

**Mitigation (falls nötig später):** `daily/` in einen lokalen Ordner (`/Users/maxim/brain/daily/`) verlegen und mit einem Symlink ins Vault anbinden. Dann ist der Write lokal schnell, und nur der fertige Output synct nach iCloud.

Wir sollten das **beobachten**, nicht präemptiv fixen.

### 3.4 Karpathy-Index-Skalierungsgrenze

Ab ~500 Artikeln wird der Ansatz "alles in einen Prompt laden" unpraktikabel. `gemme` hat 128k Kontext, das reicht theoretisch für viele Artikel — aber ab einem Punkt **verliert das Modell die Aufmerksamkeit für den Index-Hinweis** und synthesisiert aus dem Bauch heraus.

**Wann das relevant wird:** Aktuell haben wir 14 Artikel in `90_Wiki/` und 0 in `95_Gehirn/knowledge/`. Bei Maxims Nutzungsintensität könnten wir in ~6 Monaten 50–100 Artikel erreichen. In 2 Jahren 500+.

**v1.3+ Action-Item:** Spätestens bei 300 Artikeln müssen wir evaluieren, ob der Index-first-Ansatz noch skaliert. Umstieg auf RAG-Primary mit Index als Re-Ranker ist dann der Plan B.

### 4.2 Compile-Trigger-Automatisierung

Aktuell wird `tom-compile` **manuell** aufgerufen. Das ist OK für den Anfang (Maxim kontrolliert, wann und wie oft), aber langfristig soll es automatisch laufen — einmal täglich oder per git-hook.

**Varianten:**
- `launchd` Daily-Job auf dem Mac (macOS-native)
- Cron-Eintrag (einfacher, weniger macOS-idiomatisch)
- Manueller SessionEnd-Trigger (nur wenn die Session "reich" war — Heuristik nötig)

**Empfehlung:** Einfaches `launchd` daily um 18:00 lokale Zeit. Entspricht dem Default des Upstream-Tools. Macht der User rebooted es automatisch. → v1.3 Scope, wenn Brain anfängt sich zu füllen.

### 4.3 `95_Gehirn/` wird noch nicht wirklich genutzt

Das ist der **ehrlichste Befund** aus v1.2: Wir haben die Infrastruktur gebaut, aber der Brain ist noch praktisch leer (1 daily-log, 0 knowledge-Artikel).

**Das ist völlig normal und erwartet.** Der erste `tom-compile`-Lauf wird den einen daily-log destillieren, aber bis "Wissen" entsteht braucht es mehrere Wochen Nutzung.

**Action-Item für Maxim:** In den nächsten 2–4 Wochen ganz normal mit Claude Code arbeiten. Dann `tom-compile` laufen lassen und schauen, was entsteht. **Erst dann** ist die Kosten/Nutzen-Frage für den Memory-Compiler beantwortbar.

Das ist kein v1.2-Issue, aber es bleibt hängen: Der Tom-Agent in der Maximus_OS-Company ist seit v1.1 Phase 12 in einem Fehlerzustand. Tracking via **FAM-112**.

**Das bedeutet:** Wir haben aktuell **keine** Möglichkeit, den Tom-Agent in Maximus_OS dazu zu bringen, eigenständig `tom-ask` oder `tom-wiki` aufzurufen. Das ist ein offener Knoten, der v1.3 oder später gelöst werden sollte — entweder durch CTO-Debugging des Agent-States oder durch ein neues Tool-Integration-Pattern.

### 4.5 Anthropic-SDK-Subscription-Clarification (siehe 3.2)

Non-blocker, aber sollte geklärt werden, bevor `tom-compile` regelmäßig läuft. **Verantwortlich:** CEO-Agent (verify with Anthropic). **Deadline:** vor erstem `tom-compile` in Produktion.
